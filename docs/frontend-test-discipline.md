# 前端测试纪律（Frontend Test Discipline）

> 本规程是 AGENTS.md「前端测试纪律」节的展开。AI 修改 `frontend-demo/` 后必须自驱执行一轮，**不得跳过**。

## 1. 目的

防止 AI 前端改动引入回归与可维护性劣化。每次前端改动后，AI 必须自驱跑一轮清单驱动的浏览器实测：缺陷**只登记不即修**，全部清单跑完后再由用户决策修复。避免"改一个引三个"的连锁混乱。

## 2. 适用范围

仅 `narrative-engine/frontend-demo/` 目录及其直接依赖：

- `frontend-demo/` 下任意文件（index.html / views/*.js / app.js / api-*.js / mock-data.js / styles/*.css）
- 被 frontend-demo 引用的 mock 与接口约定

旧版 `visualizer-ui/` 已于 2026-08-04 删除，本规程覆盖 `frontend-demo/` 全部页面。

## 3. 触发条件

满足任一即触发一轮测试：

- AI 修改了 `frontend-demo/` 下任意文件
- AI 修改了 frontend-demo 依赖的接口/mock 数据（`mock-data.js` / `api-mock.js` / `api-client.js`）
- 用户显式要求跑前端测试轮

## 4. 五步流程

### 步骤 1：产出测试清单

- 文档路径：`docs/audits/frontend-test-runs/<YYYY-MM-DD>-<feature>.md`
- 基于本次 git diff 与受影响页面生成清单
- 清单须含：受影响页面列表、测试项（按第 5 节分类）、每项可勾选
- 模板见附录 A

### 步骤 2：逐项执行（browser_use 实操）

- 在 `narrative-engine/` 下启动服务：`node scripts/app-server.mjs --port 7421`
- browser_use 打开 `http://127.0.0.1:7421`
- 按清单逐项操作：点击 / 输入 / 导航 / 触发交互
- 每项执行后在文档中打勾 `✅`，发现问题转步骤 3
- 关键页面截图存到 `docs/audits/frontend-test-runs/shots/<YYYY-MM-DD>-<feature>/`
- 控制台错误通过 browser_use 的 `browser_console_messages` 采集

### 步骤 3：缺陷登记（禁止即修）

- 发现问题的当下，**禁止修改任何代码**
- 登记到同一测试轮文档的「缺陷登记」表
- 字段：编号 / 所属清单项 / 严重度 / 复现步骤 / 期望 / 实际 / 截图 / 状态
- 严重度定义见附录 B
- 登记后**继续执行下一项**，不得停下来修

### 步骤 4：跑完汇总

全部清单项执行完毕，在文档末尾输出小结：

- 通过 N 项 / 失败 M 项 / 跳过 K 项
- 缺陷按严重度分布（P0 x / P1 y / P2 z / P3 w）
- 一句话总体评价

### 步骤 5：修复决策（用户）

- 用户审阅缺陷表，对每条决定：**本轮修 / 下轮修 / 暂不修**
- AI 按决策执行修复，修复同样走分支策略 + 触发新一轮测试
- 标记「下轮修 / 暂不修」的缺陷同步到 `docs/audits/frontend-bug-backlog.md`

## 5. 测试项分类

| 分类 | 覆盖点 |
|------|--------|
| 功能正确性 | 按钮 / 表单 / 导航 / 数据流 / 路由切换 |
| 交互路径 | 点击 / 输入 / 拖拽 / 快捷键 / 弹层 / 选项卡 |
| 边界情况 | 空数据 / 超长文本 / 并发操作 / 错误态 / 加载态 / 空态 |
| 视觉一致性 | tokens 一致 / 对齐 / 间距 / 暗色模式 / 字体 |
| 控制台洁净 | 无 JS 报错 / 无 404 / 无未捕获 Promise / 无警告 |
| 响应式 | 常见宽度（1280 / 1440 / 1920）下布局正常 |

## 6. 与现有测试的关系

- 本规程**不替代** `tests/frontend-*.test.ts`（`frontend-demo.test.ts` / `frontend-api-client.test.ts` / `frontend-utils.test.ts`）单元测试
- 单测验证逻辑/数据流；本规程验证真实渲染与交互
- 二者互补：单测可作为步骤 2 中「逻辑项」的旁证，但**不免除浏览器实测**

## 7. 硬约束

- **禁止即修**：测试轮进行中，AI 不得修改任何代码
- **禁止跳过登记**：发现问题必须登记，不得口头描述后忽略
- **禁止声明完成未跑**：AI 声称前端改动「完成」前，必须附本轮测试轮文档链接
- **单轮单文档**：一轮测试一份文档，不合并多轮
- **截图必附**：P0/P1 缺陷必须附截图；P2/P3 视情况

## 附录 B：严重度定义

| 级别 | 含义 | 示例 |
|------|------|------|
| P0 阻断 | 核心功能不可用 / 白屏 / 崩溃 | 页面打不开、主流程报错、数据丢失 |
| P1 严重 | 主要功能受损但有 workaround | 某按钮无响应、表单提交失败但有替代路径 |
| P2 一般 | 次要功能 / 视觉问题 / 体验瑕疵 | 对齐错位、间距不一致、非关键交互卡顿 |
| P3 轻微 | 文案 / 极端边界 / 微小瑕疵 | 错别字、超长文本截断、特定分辨率下的像素偏差 |

## 附录 C：与 backlog 的同步规则

每轮测试结束后，AI 将状态为「下轮修 / 暂不修」的缺陷同步到 `docs/audits/frontend-bug-backlog.md`：

- 新增行：编号 / 首次发现轮次 / 严重度 / 页面 / 摘要 / 状态=open
- 已修复行：状态改为 fixed，附修复轮次
- 用户确认不修：状态改为 wontfix

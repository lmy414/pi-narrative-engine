## 一、需求原话与转述

> 用户原话："小说工程结构需要重新约定，区分章节，事件的粒度，让增加额外的文件区域，大纲设定等文本内容。"

**转述**：
1. **重新约定小说工程结构**：现行 v2 结构（`docs/novel-project-structure.md`）在"章节/事件的粒度"上没有清晰且一致的约定，需要重新定义。
2. **区分章节与事件的粒度**：明确"一个章节文件"与"一个事件"各自对应什么存储单元、二者边界如何。
3. **增加额外文件区域**：除正文与规则集外，为**大纲、设定等文本内容**提供约定化的文件区域，引擎与 UI 对其有明确认知。

## 二、现状查证（2026-08-08，事实与矛盾）

### 2.1 现行 v2 结构（文档声称）

```
<novel-root>/
├── novel.json          # name / engine / worldGraphDir / chaptersDir / storyTimeFormat / createdAt
├── 正文/               # 章节文件：第<N>章-<标题>.md（锚点格式）
├── 规则集.md           # 渲染器规则
├── planner 规则集.md   # planner 检索规则
├── 角色规则集.md       # 角色扮演规则
└── .pi/
    ├── world-graph-v3/ # world.db + events.jsonl + memory.md + chapter-index.json + alias-index.json
    ├── scheduler-plans/
    └── ...
```

storyTime 模型：`ch{NNN}.ev{NNN}`——ch=章节号，ev=章内事件序号；同章 ev+1，进新章 ch+1 且 ev 从 001 起；零填充保证字典序==时序。

### 2.2 粒度矛盾（代码 vs 文档 vs 实盘，已查证）

| 层面 | 声称/实际 | 证据 |
|---|---|---|
| 文档约定 | 章节级文件：`正文/第<N>章-<标题>.md`，事件以锚点段落追加进章节文件 | novel-project-structure.md §2；正文/第9章、第11章-未命名.md（文件内 `<!-- event: evt_xxx -->` 锚点分段） |
| **引擎实际** | **每事件一文件**：`chapters/${storyTime}.md`（缺省，硬编码）——`novel.json.chaptersDir` **未被消费** | `src/orchestrator.ts:630` `resolveChapterPath` 缺省 `chapters/${event.storyTime}.md` |
| 实盘数据 | **两种粒度并存**：`正文/第9章、第11章-未命名.md`（章节级） + `chapters/ch012.ev006~ev010.md`（事件级） | `d:\claude\pi-ex\novel\` 实测 |

**结论**：章节/事件的粒度在 v2 中没有被统一约定——文档、模板、引擎缺省、实盘四处不一致。`chaptersDir` 字段形同虚设（只有文档与模板在用），引擎不读它。这正是用户要求"重新约定、区分粒度"的根源。

### 2.3 现状的其他结构问题

- **规则集三件套**：项目根固定文件名（`规则集.md` / `planner 规则集.md` / `角色规则集.md`），引擎按约定文件名加载注入——无"区域"抽象，新增类型的文本内容无处安放。
- **额外文本区域（大纲/设定）**：V6 文件视图技术上已能编辑项目内任意 .md/.txt/.json，但引擎对"大纲""设定"**无认知**——无约定位置、模板不创建、不注入上下文、UI 无分组。
- **结构文档滞后**：novel-project-structure.md §2 目录树未列 `.pi/logs/`、`.pi/sessions/`、`.pi/scheduler-plans/`（实盘已存在）——违反 docs 维护约定 #4 强一致性。
- **chapter-index.json**：世界图侧已维护 `{chapter_id, title, storyTimeRange}` 章节索引，与文件粒度模型脱节（未约定如何随文件粒度变化）。

## 三、目标结构设计方向（v3 草案，供决策）

### 3.1 粒度模型（核心决策）

| 候选 | 模型 | 优点 | 代价 |
|---|---|---|---|
| **A 一章一文件** | `正文/第<N>章-<标题>.md`，事件正文以锚点段落**追加进章节文件**（v2 文档声称的模型） | 阅读单元=章节文件；文件数与章数一致，符合作者直觉；规则集可约束整章结构 | 需保证锚点/追加并发安全（已有 renderToFile 锚点机制）；长章节文件单文件体积增长 |
| **B 一事件一文件** | `正文/ch{NNN}.ev{NNN}.md`（当前引擎缺省行为） | 与 storyTime 一一对应，可追溯粒度最细；文件天然不冲突 | 文件爆炸（一章 N 个文件）；"章节"在文件系统里没有实体（需要章节索引聚合，如 chapter-index.json）；阅读体验碎片化 |
| **C 章目录+事件文件** | `正文/ch{NNN}/ev{NNN}.md` 或 `正文/ch{NNN}.ev{NNN}.md` + 章级 README/汇总 | 兼顾粒度与组织 | 双层级复杂；章级内容如何生成需另约 |

> PM 视角倾向 **A**（对齐"正文=章节文件"的作者直觉，章节文件即阅读与交付单元，事件是章内段落粒度）或 **B 显式化**（若作者要事件级追溯，则明确"一章=一目录/一索引"）。最终由用户定。

### 3.2 novel.json v3 schema 草案

```jsonc
{
  "name": "{{name}}",
  "engine": "narrative-engine",
  "engineVersion": "{{engineVersion}}",
  "worldGraphDir": ".pi/world-graph-v3",
  "storyTimeFormat": "ch{NNN}.ev{NNN}",
  "chaptersDir": "正文",                    // 语义与粒度模型绑定（章节级文件 or 事件级文件目录）
  "contentAreas": {                        // 新增：额外文本区域（键=区域名，值=相对目录）
    "outline": "大纲",                     //   大纲（卷纲/章纲）
    "setting": "设定",                     //   设定（世界观/人物/地点/物品/时间线）
    "archive": "素材"                      //   可选：素材/随笔等自定义区域
  },
  "createdAt": "{{date}}"
}
```

- 兼容性：v2 工程缺省 `contentAreas` 时仅保留 `正文`，不破坏既有项目；未知区域键保留写入（`@pi/admin` read/writeNovelJson 已允许未知扩展字段）。
- 区域文件默认约定：`大纲/README.md`（区域说明）+ 可选 `大纲/卷纲.md`、`设定/世界观.md` 等模板文件，脚手架一并创建。

### 3.3 引擎与 UI 对区域的认知（分步落地候选）

| 能力 | 说明 | 依赖 |
|---|---|---|
| 模板/脚手架 | 创建 `大纲/`、`设定/` 空目录 + 引导 README | 独立可做 |
| V6 文件视图 | 按 contentAreas 分组展示文件树（区域标题），非 .md 区域照常可编辑 | 独立可做 |
| 规则集引用 | 渲染/角色/规划规则集可显式引用区域文件（如"按 设定/人物卡.md 保持人设"） | 注入方式待定 |
| **上下文注入** | 大纲/设定摘要注入主会话与子代理上下文（前情与设定一致性的数据源） | 与 G5-1 记忆注入强关联，建议随 G5 一起做 |
| 渲染器 | 章节文件从"正文"或指定区域读取上下文（当前 renderToFile 把整个章节文件当上下文） | 依赖粒度模型 D1 |

### 3.4 现有 novel/ 工程收敛（D1 决策后的清理）

实盘 `novel/` 同时存在 `正文/第9、11章`（章节级）与 `chapters/ch012.evNNN`（事件级）——决策粒度后需二选一收敛：合并事件文件回章节文件（需按 chapter-index 或 storyTime 归组），或反向拆分；迁移前备份。此收敛亦修正 `resolveChapterPath` 的缺省路径与 `chaptersDir` 的消费关系。

## 四、开放决策点（实施前需对齐，本记录不选型）

| # | 决策点 | 候选方向 |
|---|---|---|
| D1 | **章节/事件粒度模型** | A 一章一文件+事件锚点段落（推荐） / B 一事件一文件+章节索引 / C 章目录+事件文件 |
| D2 | **区域声明方式** | novel.json `contentAreas` 映射 vs 固定约定目录（大纲/、设定/）vs 两者结合（推荐：映射为主，模板预置固定区） |

| D4 | **chaptersDir 语义修正** | 与 D1 绑定：章节级文件目录（A）或事件级文件目录（B/C）；`resolveChapterPath` 缺省值改为消费 chaptersDir 并校验存在 |
| D5 | **现有 novel/ 收敛策略** | 合并 chapters/ 事件文件回 正文/ 章节文件 / 反向拆分 / 保持并存仅文档声明（不推荐） |
| D6 | **规则集是否纳入区域模型** | 三件套留在项目根（现状，最省） / 迁入 `规则/` 区域并兼容读取旧位置（推荐渐进：v3 保留根位置，新增区域不强制迁移） |

## 五、验收标准（草案）

1. 结构文档 v3 与代码、模板、实盘一致（消灭 §2.2 四处矛盾），`chaptersDir` 被引擎真实消费。
2. 新工程脚手架创建全部区域目录（正文/大纲/设定 + 引导 README）。
3. 旧工程（缺 contentAreas）打开不破坏、可编辑、可创作。
4. 章节/事件粒度唯一约定：文件系统布局可由 storyTime 无损推导（或反之）。
5. 大纲/设定文件可被 V6 编辑，且至少一种机制（规则集引用或上下文注入）能影响生成。

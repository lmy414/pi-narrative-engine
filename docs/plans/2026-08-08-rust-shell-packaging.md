## 一、建议原话

> "后续建议：Rust 做前端壳层，进行打包。"

**转述**：用 Rust 实现**前端壳层**（桌面壳），把现有 Web 前端（frontend-demo + 本地服务）打包成可分发的桌面应用。**注意与历史的区别**：

| 方案 | 内容 | 状态 |
|---|---|---|
| 2026-08-01-frontend-rust-redesign | **Rust 重写前端**（放弃 JS 路线） | ❌ 已弃用（实际走 JS） |
| 本建议 | **Rust 做壳层**（webview 承载现有 JS 前端 + 本地服务打包） | 📋 本记录，尚早 |

壳层方案（Tauri 形态）保留全部 JS 前端存量，Rust 只负责窗口/系统集成/打包分发——与既有技术栈无冲突。

## 二、现状与关联

- `tauri-app/` 目录为预留入口，**尚未发布**；G6 产品化（Tauri sidecar 打包链路确认、跨平台验证、版本发布）仍是待办（phase2 计划 G6-1/2/3）。
- 审计残留：M20（launchVisualizer sidecar 失效）、M22（启动页端口硬编码）、M24（版本号三处不一致）、M25/M27/M28/M29（Tauri 构建残留）——若推进壳层，这批残留需一并清理。
- **打包难点盘点**（与壳层形态强相关）：
  - `better-sqlite3` 原生模块（node-gyp 编译，需随平台打包或改 pure-JS 方案）
  - `@xenova/transformers` 向量模型缓存（首次下载 ~24MB，打包 vs 运行时下载）
  - LLM API Key 存储（`auth.json`，壳层需沿用权限语义）
  - 本地服务端口（7421）生命周期管理（壳层拉起/关闭，避免残留进程与端口冲突）
  - 更新分发（无自动更新机制）
- **与问题 6 的协同点**：桌面壳可提供原生级悬浮窗/全局 UI 能力（问题 6 的悬浮对话在桌面壳下可升级为原生窗口形态），但问题 6 本身不依赖壳层。

## 三、方向草案（存档）

1. **壳层形态**：Tauri（webview + Rust，沿用 tauri-app/ 预留目录）vs 自研轻壳（Rust 静态伺服 + 系统 webview，更轻但生态少）——倾向 Tauri，复用存量目录与既有评估。
2. **服务打包策略**：本地 HTTP 服务（app-server.mjs）随壳层捆绑 Node 运行时 sidecar vs 服务进程化改造（常驻/按需拉起）——G6-1 原任务即此。
3. **与 JS 前端解耦**：壳层只做窗口与分发，前端渲染/路由/API 契约全部不动（frontend-requirements 契约不变）。

## 1. 叙事引擎：调度器+执行器架构

### 一、整体架构

**叙事引擎由调度器(Scheduler)和执行器(Executor)两部分组成。**

**调度器职责：**

- 按照用户编排的事件节点序列，读取当前节点
- 收集事件所需的世界背景条目和角色信息
- 拼接成提示词，交给执行器
- 接收执行器返回的文本输出
- 分析输出内容，识别扩散（状态变化）
- 将扩散结果写入世界书对应条目
- 根据更新后的世界状态，调度下一个事件节点
- 到达用户设置的暂停点/结束标记时停止

**执行器职责：**

- 子代理实例，接收调度器发来的提示词
- 按提示词执行事件，生成叙事文本
- 返回输出结果给调度器


### 二、关键设计决策

**调度器做扩散判断，不做内容生成**

扩散识别放在调度器而非执行器，确保扩散规则由创作者控制。可预设扩散类型（关系变化、物品状态变更、认知更新等），调度器按规则自动识别写入。

**子代理隔离**

每个事件使用独立的子代理实例，互不污染上下文。子代理仅需看到当前事件相关的世界条目，不需背负全部历史。解决长篇小说上下文爆炸问题。

**暂停点设计**

保留人在回路——创作者在每个暂停点检查扩散结果、调整世界条目、修改后续节点。


### 三、待细化：扩散识别策略

- LLM分析：再用一次LLM分析输出提取状态变化（灵活但多一层开销）
- 规则匹配：预定义扩散模板，匹配写入（高效但灵活性低）
- 混合方案：LLM粗筛+创作者确认（推荐方向）


### 世界背景的定义

**一切会在剧情中动态进行演化的内容都可以认为是世界背景。**

包括但不限于：角色信息（情感状态、认知、关系）、社会背景（制度、风气、群体关系）、设定（物理规则、魔法体系、历史事件）等。

核心特征不是"和主线逻辑无关"，而是"在剧情中动态演化"。这与之前的定义一致：角色状态被事件修改，因此角色也是世界背景的一部分——它和天气、社会规则一样，都是事件扩散的写入目标。

这直接决定了叙事引擎中世界书的数据结构：角色、场景、规则、关系都是同一层级的状态条目，用统一的 key/content/triggers 格式管理。


### 世界背景的组织形式：节点图

**每个世界条目是图上的一个节点，节点之间按相关性用边连接。检索和扩散均沿边进行。**

节点：世界条目（角色、地点、规则、关系...），每个节点有自然语言 content 字段

边：相关性连接（角色A-居住-城市B、角色A-爱上-角色C、城市B-属于-王国D...）

检索：从事件相关的节点出发，沿边 BFS/DFS 遍历 N 步，收集途经节点的 content 注入 AI 上下文

扩散：事件结果沿关联边写入目标节点，触发邻接节点的级联状态更新

**优势：**

- 不需要手动维护触发条件——图的拓扑结构本身就是检索路径
- 扩散可沿边自动传播（A死亡→关系边→C悲痛→社会边→势力格局变化）
- 可视化友好——创作者可以看到世界状态的全景图

**待细化：**

- 边的构建方式——创作者手动连线，还是从自然语言条目中自动推断？
- 遍历深度控制——沿边走几步合适？太浅遗漏信息，太深带回噪音
- 扩散级联控制——单事件触发多少级联更新？如何防止状态爆炸


### 世界知识检索与更新完整流程

**调度器（循环控制）**

① 读取当前事件节点

② 沿图边查找涉及的世界背景条目及相邻关联条目

③ 提取条目中的自然语言知识（content字段）

④ 拼接提示词，注入执行器

**执行器（文本生成）**

⑤ 接收提示词，生成叙事文本

⑥ 返回生成结果给调度器

**调度器（扩散处理）**

⑦ 分析生成结果，分离出扩散（状态变化）

⑧ 将扩散结果写回对应图节点（更新 content）

⑨ 增量更新图谱——受影响节点的边和内容

⑩ 提取下一轮事件涉及的知识，回到步骤①，直到结束标记

核心特征：图不是一次性建好的，而是随着每次事件扩散增量更新的。这与 Understand Anything 的增量指纹更新同构——每次事件就是一次图谱的快照变更。

**与世界观调研的对照：CIDOC-CRM 的事件-时间-地点-参与者模型可映射为图的节点类型；Obsidian+Dataview 的 MD+YAML 可映射为节点存储格式；Neo4j 图遍历可映射为调度器的沿边检索算法。**

## 9. 综合架构：四层蓝图

## 10. 核心循环（最终版）

**事件输入**

创作者定义当次事件需要发生什么。三要素：时间、地点、发生了什么。自然语言描述。

**调度器：查询与组装**

根据事件输入，沿世界图查询对应的背景条目，将条目知识组装为提示词，传入执行器。

**执行器：生成**

接收提示词，调用 LLM 产生输出文本，返回调度器。

**调度器：拆解与更新**

接收输出，拆解需要变更的条目，更新世界图对应节点的 content。查询下一个事件节点。

**循环 → 暂停标记**

以上流程循环执行，直到命中创作者设置的暂停标记。暂停点保留人在回路——创作者检查世界状态、调整后续事件。

循环结构：事件输入 → [调度器→执行器→调度器] → 下一个事件输入 → ... → 暂停标记

**✅ 核心循环概念验证通过**

用 Python 实现了调度器+执行器核心循环，验证了"世界图 + LLM 扩散"范式的可行性。

里程碑：事件输入→图检索→提示词拼接→LLM生成→扩散拆解→写回节点→下一个事件。全链路跑通。

## 11. 执行器附加上下文：解决事件孤立感

仅靠扩散传递状态变化不够——需要给执行器注入更多上下文，增强事件间的因果连贯性。分为三层：

**用户提供层**

事件意图：本事件要表达什么。角色弧状态：角色正处于什么转折阶段。由创作者在事件输入时一并给出，不可自动化。

**引擎自动层**

前 N 个事件摘要：调度器维护一个滑动窗口的历史摘要，每次循环自动更新并注入执行器提示词。

执行器最终拿到的提示词 = 当前世界状态（图检索） + 事件意图（用户） + 角色弧（用户） + 历史摘要（引擎）

## 12. 理论深化：背景信息如何影响事件与决策

**当前模型的盲区：执行器拿到世界状态后，AI"自行判断"角色怎么做，缺少明确的因果层。**

因果关系不是由状态自动生成的，而是由角色基于背景信息做出的决策驱动的：

世界状态 → 角色认知（知道什么）→ 角色动机（想要什么）→ 角色决策（做什么）→ 事件

**三层信息差：**

认知层——角色不知道某事（如外面暴雨）→ 错误行动 → 意外推动剧情 → 延迟扩散

动机层——角色知道但面临两难 → 抉择 → 塑造人物 → 累积扩散

决策层——角色行动但选错 → 后果 → 角色弧转变 → 即时扩散

待文献验证的方向：Genette聚焦理论（谁说/谁知道）、认知叙事学（角色心智模型）、可能世界理论（角色选择路径）。

## 13. 调研：信息差、沉默/反事件与伏笔理论

**三条研究轴心汇聚于同一命题：如何在计算系统中建模"叙事信息的策略性管理"。**

1. 信息差与戏剧反讽

- Genette聚焦理论：内聚焦天然产生信息差（读者只通过角色视角感知），外聚焦极端化信息差（连内心都进不去），零聚焦可故意隐藏信息
- Booth《小说修辞学》：不可靠叙述者——叙述者与隐含作者之间的知识/价值偏差
- NWM (2026, arXiv:2607.05577)：直接建模"谁在何时知道什么秘密"——与认知-动机-决策三层信息差高度吻合

2. 沉默/反事件/留白

- 中国古典美学："计白当黑"（书画）、"言外之意"（诗学）——沉默本身就是叙事信息
- 金圣叹"不写之写"：不直接描写反而是更深刻的描写——如不写宋江心理活动，反而使人物更丰富

3. 金圣叹草蛇灰线——最精密的前现代伏笔理论

- "隐与显的辩证"：伏笔不能太明显也不能太隐蔽——半隐半现，第一遍不经意，第二遍惊叹"原来早有暗示"
- "千里伏线"：伏笔可跨越极大叙事距离（如武松哨棒跨越数回）
- "物象作为线索"：具体物象（哨棒、解腕尖刀）每次出现既暗示未来又呼应过去
- 与Chekhov's gun的对比：契诃夫强调功能性回报，金圣叹增加了审美维度——追求"若有若无"的笔法

**对叙事引擎的启示：**

- 知识状态分层：每个角色 + 读者 + 系统，三者各自维护独立知识图——戏剧反讽可还原为这些层之间的差异
- 伏笔的后向一致性：需维护可回溯因果链——每个被planting的元素都有一条通向payoff的路径
- 草蛇灰线的"半隐半现"：对应扩散机制中"写入但不触发"的延迟扩散——状态已变但暂不注入执行器上下文

## 14. 调研：角色弧、因果延迟与累积效应

**1. 角色弧理论——对应即时扩散（决策层）**

- Campbell单一神话→Vogler英雄之旅12阶段：角色状态按阶段线性推进
- McKee"鸿沟"原理：角色每次选择产生不可逆的状态变化→事件→扩散→角色弧推进
- Truby角色网：角色不是孤立发展的，而是通过网络中其他角色的变化来映照
- 计算方向：Drama Machine (2408.01725)用LLM驱动角色驱动的互动戏剧，CHATTER系统形式化角色社会规范

**2. 因果延迟——对应延迟扩散**

- Genette时距四形态：停顿(叙事>故事)/场景(叙事=故事)/概要(叙事<故事)/省略(叙事=0)
- Rimmon-Kenan：因果延迟是制造悬念的核心手法——先展示结果，延迟揭示原因
- 计算方向：Causal Micro-Narratives (2410.05252)用因果图建模微叙事链

**3. 累积效应——对应累积扩散**

- Chekhov's Gun：引入元素必须回收——setup-payoff的强制性因果约定
- Barthes催化功能：微事件不改变核心选择但累积影响阅读体验→量变到质变
- Chatman卫星事件：围绕核心事件的小事件，删掉不影响因果但删掉失去血肉

**对叙事引擎的启示：**

- 角色弧 = 角色在世界图中的状态序列——线性推进/回退/循环三种模式需在扩散写入时区别处理（覆盖/追加/版本化）
- Genette时距 → 事件的"扩散时间戳"不应是单一的——同一事件的不同影响可以在不同时间点触发
- Chekhov's Gun → 伏笔的强制性回收——图节点需标记"planted"和"paid_off"状态，未回收的伏笔触发告警

## 15. 执行器架构升级：多角色子代理 + 渲染器

**核心变化：信息差从模拟变为结构——不是让一个AI假装角色知道不同的事，而是每个角色拥有独立的子代理实例，调度器按信息差定向分配知识。**

架构流程：

① 调度器定向分配知识——按Genette聚焦理论，每角色子代理只拿到该角色视角已知的世界条目子集

② 角色子代理并行交互——角色扮演产出结构化数据（行为、对话、情绪状态变化），不直接生成最终文本

③ 结构化数据双路输出：一路回调度器更新世界图，一路交渲染器

④ 渲染器将结构化数据渲染为最终叙事文本（对应骨骼/渲染双层架构）

**理论依据：**

- Oz Project可信代理：角色不需要"智能"，只需"看起来有生命"——隔离的子代理天然模拟有限理性和独立人格
- Genette内聚焦：信息差从叙事技巧变为架构原则——调度器按角色权限过滤世界条目后再注入
- MEXICA故事生成系统：语义层(结构化)和文本层分离——角色交互=语义层，渲染器=文本层
- NWM知识分层模型：角色/读者/系统三层知识状态，角色子代理天然对应"角色层"

与之前架构的对比：

旧：执行器(单代理) → 直接生成文本 → 调度器从文本中提取扩散（扩散提取不可靠）

新：多角色子代理 → 结构化输出 → 扩散天然以结构化形式呈现 → 写回世界图（扩散提取可靠化）

## 16. 概念验证发现：事件粒度与叙事连续性

**短篇测试通过，但暴露了长篇的关键问题：事件之间不连续。**

当前架构：每个事件独立运行，渲染器在事件结束后介入。输出是"事件摘要串"，靠时间标签（第二天/第三天）缝合。长篇里这不可接受——读者读到的不是故事，是摘要。

根因：渲染器在循环外部。但叙事里过渡本身就是内容——事件A如何滑入事件B，那个"滑入"就是叙事。

**解决方向：**

- 渲染器提升到循环内部——按场景为单位持续输出，不做事件级分段
- 事件粒度细化——引入"微事件"（比当前事件粒度更细的推进单元）
- 缝合机制——调度器在事件间隙插入过渡微事件，让事件链自然流动

待验证：渲染器连续输出模式下，扩散提取的时机如何调整。

## 17. 实现路径：独立 π 智能体（修正）

**叙事引擎不是 Hermes 的扩展，而是一个独立的 π（智能体）。**

有自己的身份、系统提示词、运行模式。作为独立实例运行，与 Hermes 并列。

形态：一个独立 AI 智能体，内置叙事引擎循环。用户通过对话界面与之交互——编辑模式讨论设定、引擎模式驱动叙事推进。

先不做 GUI，通过对话界面验证闭环，后续再升级到蓝图式节点编辑器。

技术基底可沿用 Hermes 框架（Skill/Profile/delegate_task/自定义 Tools），但身份是独立的——不是一个工具，是一个搭档。

## 19. Pi 扩展机制——叙事引擎落地分析

**Pi 的架构与叙事引擎需求高度匹配：**

1. 自定义 Agent（Markdown + YAML）

- Agent 定义在 ~/.pi/agent/agents/*.md，YAML frontmatter 配 model/tools，body 写系统提示词
- 调度器、渲染器、每个角色子代理都可以定义为一个独立 Agent

2. 原生多模型支持

- 每个 Agent 可以独立指定模型——调度器用最强模型，角色代理用轻量模型
- 正是叙事引擎需要的：调度器深思熟虑，角色代理快速响应

3. 自定义工具（pi.registerTool + TypeBox）

- world_graph_query / diffusion_write / narrative_step 可注册为自定义工具
- TypeBox 提供类型安全和参数验证

4. 子代理系统（独立进程 + JSON 行协议）

- 角色代理作为独立子代理 spawn，通过 JSON 行协议通信
- 天然支持角色间的上下文隔离

5. 状态持久化（JSONL + 树形分支）

- 世界图可存为 JSON 文件，扩散操作以 JSONL 追加
- 支持分支——尝试不同叙事方向

6. Agent 循环钩子（15+ hooks）

- 可自定义叙事引擎的特殊循环逻辑

结论：Pi 已具备叙事引擎所需的全部基建。开发路径：定义 Agent（调度器+渲染器+角色）→ 注册自定义 Tools → 编写世界图 JSON 存储 → 串联循环。

## 20. Pi 深度研究——叙事引擎落地路径

**Pi（earendil-works/pi，71k stars）是一个终端 AI 编码 agent 框架。**

设计哲学："极简内核，最大可扩展"——子代理、plan mode、MCP 等都不内置，全部通过 TypeScript 扩展实现。MIT 协议。

**叙事引擎直接可用的能力：**

Extensions（核心扩展机制）

- pi.registerTool() + TypeBox schema → world_graph_query / diffusion_write / narrative_step
- 支持流式更新、前后钩子、异步后台任务

Skills（兼容 Claude Code/Codex 格式）

- 调度器逻辑、角色定义可写为 Skill 文档，自动加载

Orchestrator（多 Agent 编排）

- 独立进程 + JSON 行协议通信 → 角色子代理天然适配

状态持久化（JSONL 树型 + 分支）

- 世界图每次扩散追加一行 JSONL，支持分支——尝试不同叙事方向

25+ Provider、运行时切换模型

- 调度器用最强模型，角色代理用轻量模型——一个 Pi 实例内原生支持

SDK 模式（createAgentSession）

- 可将叙事引擎嵌入自定义应用，后续做独立桌面 App 的路径

开发路径：安装 Pi → 创建 Extensions（注册叙事工具）→ 创建 Skills（调度器+角色定义）→ 世界图 JSONL 存储 → Orchestrator 串联角色代理 → SDK 模式包装。

## 21. 核心循环增加：语义理解层

**在事件输入之前增加一层语义理解。**

用户自然语言描述 → 语义理解层解析 → 结构化事件输入（五要素）→ 调度器 → ...

**语义理解层职责：**

从自然语言中提取时间、地点、发生了什么、事件意图、涉及角色

将模糊描述转化为调度器可执行的结构化事件节点

自动匹配世界图中已有角色/地点，检测新增条目

这让整个引擎的入口从"表单填写"变成"对话"——创作者只需用自然语言说想发生什么，语义层自动组织为调度器的标准输入。

## 22. 语义理解层：意图分类

**语义层需要区分的五种用户意图：**

- 新增事件："接下来..." → 追加到事件序列末尾
- 修改事件："上一段改成..." → 定位事件N，替换角色行为参数
- 插入事件："在A和B之间加..." → 事件序列中插入新节点
- 查询世界："苏晚现在和谁关系最好？" → 读取世界图，不操作事件
- 删除事件："这段删了" → 移除节点，回溯对应扩散

最复杂的是修改事件——修改后需要级联撤销该事件之后的所有扩散，重新从修改点执行循环。这要求世界图支持分支和回退。

**循环模式修正：取消自动推进，改为对话驱动。**

用户每次输入触发一轮循环 → 引擎输出文本+世界图状态 → 等待用户下一次输入。不输入不触发。

好处：每轮输出后用户可检查、可修改上轮、可改变方向。完全的人在回路。

## 23. 渲染器设计修正

**渲染器是有状态、有记忆的独立子代理实例（类似角色代理持久化）。**

**关键能力：**

1. 感知操作类型——语义层将"新增/修改"意图传递给渲染器。新增时续写，修改时定位到对应段落重写。

2. 持有全文上下文——记住自己写过的所有内容，保持风格和叙事连续性。

3. 独立持久化——作为子代理实例，跨事件保持对话历史和写作记忆。

新增模式：拿到结构化数据+已有全文→续写新段落，保持风格连贯。

修改模式：拿到结构化数据+上下文→定位目标段落→重写，前后衔接。

## 24. 上下文压缩策略：按事件久远度分层

**基于图事件的久远度压缩，不是一刀切。**

最近N个事件：保留完整记忆（角色对话、情绪细节、原文）。

较早事件：压缩为逻辑叙事（因果链摘要、状态变化记录、关键节点）。

早期事件：高度压缩为因果骨架（谁做了什么，扩散了什么）。

好处：渲染器始终能看到最近事件的完整文本——保持风格连贯；同时不会被无限制膨胀的全文上下文淹没。

## 25. 世界图中角色节点的特殊结构

**角色节点不是普通的 key/content 条目，而是有结构的：**

**基础设定（酒馆角色卡）— 性格、背景、说话风格、外貌… 始终注入角色子代理**

**动态记忆 — 该角色经历过的事件（压缩摘要），按久远度分层**

**当前状态 — 情绪、关系值、位置… 随扩散实时更新**

调度器分配知识时：基础设定始终注入，动态记忆按久远度压缩，当前状态从世界图实时读取。

## 26. 规则引擎参考：EmaoNovel

**EmaoNovel 的规则引擎不是传统代码实现，而是声明式 Markdown 系统 + AI 推理引擎。可借鉴到叙事引擎：**

- 规则存储：工作目录下 .narrative/rules/，按功能分层（角色约束/世界观一致性/风格控制/禁止模式）
- 规则加载：顺序加载 + 优先级链，AI 语义匹配对应规则
- 自检节点：渲染前自检（是否违反角色约束？）+ 写入 narrative.txt 后自检（是否与上段衔接？）
- 自然语言管理：用户说"加一条规则：苏晚不会主动表白" → 语义层解析 → 写入 .narrative/rules/character.md
- 项目隔离：切换工作目录即切换规则集

## 27. 产品定位：交互式叙事

**赛道不是"AI写作工具"（帮人写完），而是"交互式叙事"（帮人进入世界）。**

**核心差异：**

AI小说工具：流水线——进去一个prompt，出来一篇文本。AI替你写完，你是读者。

交互式叙事：沙盒——进去一个世界，你做选择，世界用扩散回应。AI构建世界，你是玩家/导演。

引擎天然适配：分支选择系统、信息差驱动的角色反应、扩散因果的连锁效应——这些东西在"AI帮你写"场景是杀鸡用牛刀，在"你在世界里做选择"场景是核心体验。

## 28. 世界背景的分层

**世界条目按四层组织，控制检索精度和扩散范围：**

**角色层**

- 事件涉及的角色 → 始终检索全部三层（基础设定+动态记忆+当前状态）
- 状态变化 → 写回角色节点的当前状态和动态记忆

**角色互动物层**

- 角色持有、使用、接触的物品 → 事件中涉及才检索
- 状态变化 → 写回该物节点。例：诺艾尔花掉一枚铜币→钱袋状态更新

**非角色交互物层**

- 场景中的氛围元素：天气、人群、装饰 → 场景切换时检索，作为环境上下文注入
- 不变化，仅描写

**背景环境层**

- 世界规则和宏观氛围：晶石会发光、工会等级制度 → 始终注入
- 极少变，只有大事件触发。类似规则层，是约束而非数据

## 29. 上下文压缩策略（按世界层级）

**结合四层世界背景，压缩策略按层级分别处理：**

**角色层**

- 最近N个事件：完整记忆（对话+情绪+细节）
- 较早事件：压缩为角色状态摘要
- 早期事件：因果骨架（做了什么+扩散了什么）

**角色互动物层**

- 最近N个事件：完整状态（铜币剩余数、武器状态）
- 较早事件：仅保留当前状态值，不记录历史变化
- 早期事件：删除（旧物状态不参与叙事）

**非角色交互物层**

- 不压缩，因为换景时才触发检索。旧场景的氛围无关当前叙事

**背景环境层**

- 不压缩，因为它是规则不是数据。累积但不衰减

核心逻辑：角色是主角→记忆衰减但不丢；互动物只保留当前态→历史无用；非互动物和背景不压缩。

## 30. 长期方向：MCP 工具化

当前依赖 Pi 生态，长期目标做成标准 MCP（Model Context Protocol）工具。

好处：不绑定任何特定平台。Claude Desktop、Hermes、Pi、VS Code——支持 MCP 的地方都能运行叙事引擎。用户选生态，不是生态选用户。

## 31. 角色定义：迁移酒馆角色卡

**酒馆 V2 角色卡格式 → 叙事引擎角色节点的三层结构，直接复用：**

**基础设定（始终注入子代理）**

- 酒馆的 description + personality → 引擎的角色卡 json
- 酒馆的 mes_example → 角色说话风格的 Few-shot 模板
- 酒馆的 post_history_instructions → 规则引擎的自检约束

**动态记忆（按久远度压缩后注入）**

- 酒馆没有这一层，引擎新增。记录角色经历过的事件摘要

**当前状态（实时读取）**

- 酒馆也没有。情绪/关系值/位置，随每次扩散更新

最大的区别：酒馆的 scenario 是固定的，引擎的 scenario 由调度器每轮动态注入——因为世界状态在变化。

## 1. 引擎设计目标

基于 pi 扩展生态的可视化叙事引擎。基于作者原创的**事件-扩散理论**设计。

## 2. 事件-扩散理论（核心思想）

理论文档: https://emaostudio.online/study-room/event-diffusion-model

### 2.1 事件的正式定义

**事件 = 任何对背景信息层产生扩散（写入状态）的节点。**

判断标准：是否有状态写入——正向判断该节点是否改变了背景信息层中的任何字段。

此定义的特点：
- 主体不限：角色行为、自然事件、偶然事件均可
- 不要求意图：地震不是角色意图，但它改变世界状态
- 不要求选择分叉：放弃本身也是状态写入
- 不纠结变化大小：只看是否有新状态写入

以此绕过叙事学中事件的三个经典争议：变化说、选择说、意图说。

### 2.2 扩散机制

- **事件（Event）**: 发生了什么。叙事的最小行为单元。一个事件是可执行的动作，携带角色、背景等参数信息。
- **扩散（Diffusion）**: 结果如何。事件完成后，结果向背景信息层传播。扩散不是叙事终点，而是连接事件与事件的因果桥梁。
- **背景信息层（Context Layer）**: 每个故事都有角色背景、事件背景、世界观背景等信息。事件完成后，对应结果扩散到对应背景内，影响下一事件的发生。

实例：A 对 B 说出"我喜欢你"
- 扩散到关系层：B 对 A 的关系状态 = 羞涩接受
- 影响下一个事件：B 回答"才不是因为可怜你才答应的"

### 2.3 骨骼与渲染：双层架构

- **骨骼层**（事件→扩散→事件→扩散→……）：叙事者通过事件链推进故事行为。每个事件的扩散结果写入背景状态，触发或约束下一事件。这是叙事的因果骨架——删则断裂。
- **渲染层**（留白、描写、氛围、抒情、闲笔）：删而不影响因果链的内容属于渲染层。渲染寄生在事件间隙——存在于上一事件的扩散已完成、下一事件尚未触发的时间窗口。其功能不是推进剧情，而是控制叙事节奏。

事件+扩散负责"发生了什么"，渲染负责"怎么发生的"。

### 2.4 删则检验的精确化

检验对象不是文字本身，而是世界背景的状态条目。

判断流程：读取一段文本 → 识别是否有信息写入世界背景字段 → 该字段在后续事件中是否被引用？
- 是 = 事件分量
- 否 = 渲染分量

以下雨为例：
- 若下雨导致角色无法出门进而触发下一事件 → 下雨必须写入世界天气状态字段 → 事件分量
- 若下雨仅是背景氛围描写，无后续因果依赖 → 不写入 → 渲染分量

同一段文字中事件与渲染可共存：窗外下起了雨中，天气状态变更是事件分量，雨声描写是渲染分量。

### 2.5 世界背景的工程化表达

参考酒馆（SillyTavern）世界书框架，采用结构化自然语言条目。

条目结构：`key`（触发键）/ `content`（自然语言状态）/ `priority`（优先级）/ `triggers`（触发条件）

在模型中的作用：事件执行 → 扩散写入条目 content → 下个事件触发时匹配条目注入 AI 上下文 → AI 基于世界状态生成渲染层。

**与酒馆的根本区别：动态膨胀。** 世界背景不是预设的静态结构，而是随着叙事推进持续膨胀和演化的活体系统。膨胀来源分为事件扩散自动变化和作者人为操作两部分。

### 2.6 故事时间与叙事时间的分离

事件→扩散模型描述的是**故事时间（histoire）**——因果依赖不因叙事技巧而改变。倒叙、插叙、多线并行等属于**叙事时间（recit）**层面的操作。

核心模型无需修改，只需增设呈现层：
- 底层因果图按故事时间排列
- 上层呈现顺序控制叙事时间编排

具体操作：
- 倒叙：因果链不变，上层标记为倒序展示
- 插叙：插叙段作为独立子事件链，挂载到主链间隙
- 多线并行：多条因果链各自推进，交叉点标记同步依赖
- 嵌套叙事：内层故事作为外层事件节点的子图

### 2.7 三个关键澄清（理论→工程衔接）

#### 2.7.1 事件粒度：由用户输入宽泛度决定

**事件没有粒度的区分**——事件的大小来源于用户输入的宽泛度。

> "你给的叙事指令越精确，AI 自由空间越小，最终成果更加符合作者的想法；越模糊，AI 能自由发挥的空间越多。具体怎么给，就看大家自己对故事预期内容的掌控想法了。"

- 用户如果说只是让角色说了一句话，那么一句话就是一个事件
- 如果用户输入内包括了明确的交互或者内容，那么这也是一个事件
- 事件的边界 = 用户的单次输入边界

**工程意义**：引擎不需要判定"这是不是一个完整事件"——用户输入即事件。引擎的任务是基于这个输入走完一轮循环。

#### 2.7.2 扩散的因果追踪：扩散字段记录来源和影响

**扩散依赖边关系进行**——事件 E 的扩散通过边传播到后续事件 F。

额外的追踪机制：**维护一个扩散字段，记录扩散来源和影响**。

- 扩散字段记录"这个扩散来自哪个事件"（来源）
- 扩散字段记录"这个扩散影响了哪些后续事件/节点"（影响）

**工程意义**：这就是难题5（任意事件重写）的解法基础——通过扩散字段建立因果链的可追溯性，回放时知道哪些后续数据依赖被回退事件的扩散。

#### 2.7.3 用户操作与口述等价，真问题是数据冲突

**用户操作和口述都属于用户输入，等价的。**

- 用户口述事件 → 走引擎循环 → 扩散写入
- 用户直接编辑节点/边 → 绕过引擎 → 直接写入

**要解决的问题不是"哪种算数"，而是**：用户通过节点的编辑，绕过了引擎写入扩散的这一操作，需要解决的是数据之间的冲突。

**工程意义**：这重新定义了难题10（用户编辑与引擎变更的融合）——核心不是来源标记或优先级，而是**扩散一致性**：用户编辑产生的隐含扩散，与引擎自动写入的扩散，怎么协调成一个一致的世界状态。

## 3. 引擎运行机制与工程落地

理论设计文档: https://emaostudio.online/study-room/narrative-engine-architecture

### 3.1 三模块架构

#### 调度器（Scheduler）—— 状态管理中心
- 接收事件输入（**五要素**：时间、地点、发生了什么、事件意图、角色弧状态）
- 沿世界图检索相关背景条目（节点+边遍历）
- 拼接提示词：世界状态 + 事件意图 + 角色弧 + 历史摘要
- 接收执行器输出，拆解扩散（状态变化），写回世界图节点
- 增量更新图谱，查询下一事件节点，循环直到暂停标记

#### 执行器（Executor）—— 多角色子代理
- 每个角色一个独立子代理实例，**跨事件持久化**（保持对话历史和记忆）
- 调度器按**信息差**（Genette 聚焦理论）定向分配知识——每角色只获取该角色已知的世界条目子集
- 角色子代理之间角色扮演交互，产出**结构化数据**（非自然语言文本）
- 结构化格式：`{ actor, action, target, emotion, relation_update, thought }`

#### 渲染器（Renderer）—— 文本输出层
- 接收所有角色子代理的结构化输出
- 将结构化数据渲染为自然语言叙事文本
- 产出可直接阅读的最终文本，支持导出 Markdown/Word

### 3.2 核心循环

```
事件输入
  → 调度器定向分配知识
  → 角色子代理交互（结构化输出）
  → 调度器提取扩散更新世界图
  → 渲染器生成文本
  → 下个事件（子代理实例保留）
  → 暂停标记（人在回路）
```

### 3.3 工程落地的关键改变

**事件输入唯一来源是用户的口述**——用户口述一个事件，引擎按照流程更新事件状态，给出最后的文本，然后用户再口述下一个事件。这是循环流程的实际运行方式。

### 3.4 为什么这样设计

#### 信息差从模拟变为结构
不是让一个 AI 假装角色知道不同的事，而是每个角色拥有独立的子代理实例，调度器按信息差定向分配知识。信息差是真实存在的。

#### 扩散提取从不可靠变为可靠
- 旧方案：执行器输出自然语言文本 → 调度器从中"猜"扩散
- 新方案：角色子代理直接输出结构化数据，扩散天然以结构化形式呈现

#### 角色代理持久化
每个角色一个独立实例，事件之间保持对话历史和记忆。只接收增量信息（变化了的世界状态 + 当前事件上下文），不全量刷新。

### 3.5 理论依据

- **Oz Project 可信代理**：角色不需要"智能"，只需"看起来有生命"
- **Genette 内聚焦**：信息差从叙事技巧变为架构原则
- **MEXICA 故事生成系统**：语义层（结构化）和文本层分离
- **NWM 知识分层模型**：角色/读者/系统三层知识状态

### 3.6 后续待办（理论层面）

- 事件粒度与叙事连续性：渲染器提升到循环内部，微事件缝合
- 扩散类型学形式化：即时/延迟/累积/条件四种扩散的精确定义
- 图自动构建：边的创建是手工还是自动推断
- 多线并行调度：多条因果链的协调推进
- 世界图管理：检索注入、非破坏性更新（REAL）、溯源锚定（Eywa）

## 4. V0.01 版本设计简要（已验证核心循环可行）

> V0.01 代码保留在远程仓库 `legacy` 分支，作为参考实现。
> **关键结论：V0.01 验证了核心循环是可行的，新架构应保留这个核心循环。**
>
> 官方介绍文档: https://emaostudio.online/study-room/pi-narrative-engine-intro
> GitHub: https://github.com/lmy414/pi-narrative-engine

### 4.0 项目简介

Pi Narrative Engine 是基于 Pi Agent 框架的叙事引擎扩展。用户用自然语言输入（如"诺艾尔去武器店"），引擎自动执行七步流水线，产出叙事文本。GPL-3.0 开源，纯 TypeScript。

整个引擎的架构设计直接映射了叙事引擎的理论模型（事件-扩散理论 + 调度器/执行器/渲染器三模块架构）：

- **世界图（world-graph.ts）**：唯一状态中心。JSON 文件存储 + 内部 Git 仓库做版本管理。支持角色节点（三层结构：基础设定 + 动态记忆 + 当前状态）、边（关系连接）、规则条目。非破坏性写回——emotion/location 覆盖、relationships 增量、knowledge 追加。
- **调度器（scheduler.ts）**：独立 Agent 实例，分两个 LLM 调用。plan 阶段按信息差为每个角色分配 visible_entry_ids 和行动指令；diffuse 阶段审视所有角色输出，产出 Diffusion 数组，写入世界图。
- **角色子代理池（role-pool.ts）**：每个角色一个持久化 Agent 实例。调度器按信息差分配知识后，各角色 Agent 在自己可见的世界条目内演出。输出结构化数据（action/target/emotion/relation_update/thought），而非自然语言文本。
- **渲染器（renderer.ts）**：独立 Agent 实例。接收所有角色的结构化输出，渲染为叙事散文，写入 narrative.txt。拥有全文上下文，按事件久远度压缩。

技术栈特点：
- TypeScript，8 个源文件 + 3 个提示词文件
- 作为 Pi 扩展运行（非独立包）
- 支持导入 SillyTavern V2 角色卡 + 世界书
- Eywa 溯源记忆：每条记忆携带 eventId + timestamp
- 世界图以 Git 仓库管理，每条扩散可回溯

V0.01 当时的局限（V2 后续有改进）：
- 仅实现 add 和 query 意图，modify/insert/delete 流水线待完成
- 角色交互为串行（非并行）
- 记忆衰减（recent→mid→far）尚未实现

### 4.1 架构组成

```
用户："让张三去酒馆"
  ↓
主 LLM（元 AI）理解意图 → 调用 narrative_step({intent:"add", ...})
  ↓
narrative_step.execute 自动编排七步流水线：

步骤1  BFS 检索 → worldEntries
步骤2  调度器.plan（LLM #1）→ Schedule
步骤3  角色池.interact（每个角色独立 LLM）→ StructuredOutput[]
步骤4  调度器.diffuse（LLM #2）→ Diffusion[]
步骤5  graph.writeBack（语义化扩散）
步骤6  graph.commit（git）
步骤7  渲染器.render（LLM #3）→ 叙事文本
  ↓
返回主 LLM → 呈现给用户
```

### 4.3 上下文隔离机制

调度器、角色池、渲染器都是独立 `Agent` 实例，`messages = []`，与主会话完全隔离。主会话的代码对话、通用问答不会污染这些子代理。主 LLM 只通过 `narrative_step` 的结构化参数与流水线通信。

### 4.4 信息差实现

调度器在 `plan` 阶段为每个角色分配可见的世界条目（`visible_entry_ids`）。角色池在构造 user message 时按此过滤，确保角色只能看到自己应该知道的信息。

- 调度器 `plan` 工具 schema：`{ role_assignments: [{ role, visible_entry_ids, instructions }], render_style, focus }`
- 角色只能看到分配给自己的世界条目，看不到别的角色的内心独白或私密状态

### 4.5 角色子代理持久化

每个角色一个独立 `Agent` 实例，跨事件复用：
- 角色卡（V2 spec）+ 当前状态（emotion/location/relationships/knowledge）+ 记忆（recent/mid/far 三段距离）
- 只接收增量信息（变化了的世界状态 + 当前事件上下文），不全量刷新
- rollback 后清空所有子代理累积上下文，下次从回退后的世界图重建

### 4.6 结构化输出（扩散天然以结构化形式呈现）

角色子代理通过 `character_action` 工具输出：
```
{ actor, action, target, emotion, relation_update: { target, delta }, thought }
```

调度器 `diffuse` 工具基于角色输出，分配世界扩散：
```
{ diffusions: [{ node_id, field, new_value, reason }] }
```

field 支持：
- `state.emotion`（角色情绪，覆盖）
- `state.location`（角色位置，覆盖）
- `state.relationships.<对象名>`（角色关系，增量；`+0.3` / `-0.5`）
- `state.knowledge`（角色知识，追加）
- `content`（地点状态，追加版本并覆盖当前）

### 4.7 世界图（唯一状态中心）

```
.pi/world-graph/              # 独立 git repo，每次事件 commit
├── characters/               # 角色 JSON（V2 卡 + narrative_engine 扩展数据）
├── locations/                # 地点 JSON（带 versions 历史版本）
├── events.json               # 事件列表
├── relations.json            # 角色关系图（带 versions 历史版本）
├── rules.json                # 世界规则
├── narrative.txt             # 渲染产物（追加模式）
└── .git/
```

- 内存缓存（session 内有效）：characterCache / eventsCache / relationsCache / rulesCache
- BFS 检索：`MAX_BFS_DEPTH = 3`，从事件角色出发遍历关系图收集相关世界条目
- 每次事件触发 `git add -A && git commit`，支持回退到任意历史点

### 4.8 五种意图与 rollback 语义

| 意图 | 说明 |
|---|---|
| add | 追加新事件 |
| modify | 回退到目标事件之前，用新参数重新执行该事件（后续事件丢失，需手动重放） |
| insert | 回退到目标事件之后（保留目标事件），插入新事件 |
| delete | 回退到目标事件之前，删除该事件及其后续，不走流水线 |
| query | 返回世界图概览（角色 + 事件列表），不走流水线 |

rollback 语义：
- `rollback(eventId)`：`git reset --hard <commitSha>^` + 删除目标事件及之后 → 用于 modify/delete
- `rollbackToAfter(eventId)`：`git reset --hard <commitSha>` + 删除目标事件之后（保留目标事件）→ 用于 insert
- rollback 后清空所有子代理（scheduler/rolePool/renderer）累积上下文

**限制**：modify/insert/delete 后的后续事件不会自动重放（需手动重新添加）。

### 4.9 工程层（规则系统）

小说工程不只是事件流——还有作品定位、叙事约束、文风规范、质量门。由工程层的 `novel.yaml` + `规则/` 目录定义。

```
my-novel/
├── novel.yaml              # 作品元信息（类型/尺度/CP/结局/基底指令）
├── 规则/
│   ├── 总规则.md           # 优先级 + 加载顺序 + 冲突处理（给所有代理）
│   ├── 内容规则.md         # 角色关系 + 剧情红线 + 世界观一致性 + 术语（给调度器+角色）
│   ├── 文风规则.md         # 文风规范 + 参考文风 + 禁止词/敏感词（给渲染器）
│   ├── 检查清单.md         # 渲染后自检项（给渲染器）
│   └── 规则变更日志.jsonl  # 规则增量演化记录
├── 设定/
│   ├── 世界观.md
│   ├── 角色/               # 软链到 .pi/world-graph/characters/
│   └── 大纲.md
└── 正文/
    └── 第01章.md
```

规则按消费者分类注入：
- 总规则 + novel.yaml.base_directive → 所有代理（基底）
- 内容规则 → 调度器 + 角色（plan + role 阶段）
- 文风规则 → 渲染器（render 阶段）
- 检查清单 → 渲染器（渲染后自检）

**规则可替换**：RuleLoader 按目录扫描 `.md` 文件，不硬编码文件名。换文件内容 = 换规则，下次 `narrative_step` 即生效。

**规则增量演化**：用户说"诺艾尔不该说脏话"，主 LLM 调用 `add_rule` 工具自动路由到对应文件并写变更日志，下次 `narrative_step` 即生效。

### 4.10 V0.01 的核心贡献

## 6. 工程面临的核心难题（新架构必须解决）

> **这才是真正的设计资产。** V0.01 验证了核心循环可行，V2/V3 尝试解决以下难题但代码已丢失。
> 新架构的核心任务就是回答这些问题。

### 6.1 五大主要难题

#### 难题 1：世界图怎么记录？

**问题**：
- 世界图怎么记录，特别是长篇的情况下，怎么保证各个节点稳定。
- 节点稳定性是核心——长篇小说事件数千上万，节点不能因为后期的扩散而丢失或错乱。

**关联设计维度**：
- 节点 ID 策略（稳定 vs 可变）
- 节点分层（角色/物品/地点/背景/...）
- 边的 schema（关系 + 状态演化追踪）
- 存储格式（JSON 文件 / SQLite / ...）
- 版本管理（Git / 内置版本字段 / ...）

#### 难题 2：调度器怎么检索？

**问题**：
- 调度器怎么检索，怎么保证能检索到需要的数据。
- 同时正确地分配给各自的角色子代理。

**关联设计维度**：
- 检索算法（BFS / BM25 / Vector / 混合）
- 检索种子（事件角色 + 地点 + ...）
- 检索深度与剪枝
- 信息差分配策略（visible_entry_ids 的生成）
- 检索质量评估（怎么知道检索到了"需要"的数据）

#### 难题 3：角色子代理怎么扮演？

**问题**：
- 子代理应该有什么样的信息。
- 应该怎么去扮演。

**关联设计维度**：
- 子代理的 system prompt 构成（角色卡 + 状态 + 规则 + ...）
- 子代理的 memory 结构（recent/mid/far？事件级？时间级？）
- 子代理之间的交互方式（串行/并行/自由对话/结构化轮次）
- 子代理的输出格式（结构化数据 vs 自然语言）
- 子代理的持久化策略（跨事件 vs 每事件重建）
- 子代理的"扮演"定义（Oz Project 可信代理？意图驱动？情绪驱动？）

#### 难题 4：演出生成的数据怎么写回？

**问题**：
- 演出生成的数据怎么写回。
- 怎么保证更新的节点正确。

**关联设计维度**：
- 扩散提取方式（子代理直接输出结构化 / 调度器从自然语言提取）
- 写回语义（覆盖 / 增量 / 追加版本）
- 字段级写回策略（emotion 覆盖、relationships 增量、knowledge 追加、location 覆盖）
- 非破坏性更新（保留历史版本）
- 溯源锚定（每条记忆/扩散携带 eventId + timestamp）
- 写回正确性验证（怎么知道扩散写对了节点）

#### 难题 5：任意事件重写

**问题**：
- 要支持任意事件重写。
- 这个事件节点后续的节点数据应该怎么处理。
- 世界图应该怎么回放。

**关联设计维度**：
- rollback 语义（回退到事件之前/之后）
- 后续事件处理（手动重放 / 自动重放 / 直接丢弃）
- 世界图回放（git reset / 状态快照 / 事件重放）
- 子代理状态处理（清空重建 / 回退到对应时间点）
- 章节文件处理（截断到对应位置）
- 伏笔/累积器处理（回退时怎么处理已触发的伏笔）

## 7. V2/V3 踩过的坑（新架构要避免）

> 这些是已知的工程陷阱，新架构设计时必须考虑规避方案。

### 7.1 文件名与编码
- **全角空格章节文件名**导致引擎无法识别，重复创建章节。新架构：文件名规范 + 严格校验。
- **PowerShell 中文编码**导致脚本解析失败。新架构：脚本输出用英文，或显式设置 UTF-8。

### 7.2 LLM 调用可靠性
- **LLM 工具调用参数缺失**（relations/entities/events/warnings 字段可能 omit）→ 用 `?? []` 兜底处理 undefined iterable。
- **LLM 返回文本而非工具调用**即使有 schema 约束 → 设置 `thinkingLevel: "minimal"` + timeout 600s + system prompt 强化"必须调用工具"。
- **大文本 chunk 12000 tokens 导致 LLM 超时** → 降到 8000 tokens per chunk。

### 7.3 扩散提取可靠性
- **从自然语言"猜"扩散不可靠**（V0.01 之前的方式）→ 子代理直接输出结构化数据，扩散天然以结构化形式呈现。
- **post-event LLM 提取**（如 Graphiti 的 extract_nodes/edges）被禁止 → 扩散必须由子代理实时输出。

### 7.4 Web 框架
- **koa-connect wrapper 导致 ctx 泄漏** → 原生 Koa 重写，不要包装 Express 中间件。

### 7.5 向量数据库
- **小规模（≤1000 节点）不需要向量数据库** → 内存中余弦相似度 + JSON 内嵌向量就够了。

### 7.6 子代理管理
- **子代理必须信息隔离**，每个子代理只接收自己的状态和可见场景数据。
- **子代理必须跨事件持久化**，只接收增量状态更新，不全量刷新。
- **主会话不参与叙事**，只做意图理解和转发/重写用户输入。

### 7.7 伏笔机制
- **伏笔必须完全隔离**，在任何检索上下文中都不可见，直到用户显式触发。
- **Diffusion 实时写入，Impacts 用户控制触发**——这两者必须分离。

> 这些是已确定的设计约束，新架构必须遵守。

### 8.0 编码八荣八耻（最高优先级，贯穿所有工程活动）

> 项目核心约束，优先于一切设计决策与工程实践。

- **以新增冗余为耻，以复用存量为荣** —— 优先复用现有代码，不新增冗余
- **以省略校验为耻，以完备测例为荣** —— 不省略校验，测试用例要完备
- **以乱改架构为耻，以恪守规范为荣** —— 不乱改架构，恪守既定规范
- **以不懂装懂为耻，以坦诚存疑为荣** —— 不懂不装懂，坦诚标记存疑
- **以批量乱改为耻，以分步迭代为荣** —— 不批量乱改，分步迭代推进

### 8.1 理论约束
- 基于**事件-扩散理论**：事件 = 对背景信息层产生扩散的节点；扩散 = 状态向背景信息层传播
- 基于**调度器/执行器/渲染器三模块架构**
- **骨骼/渲染双层**：事件+扩散是骨骼（删则断裂），渲染层寄生在事件间隙
- **故事时间与叙事时间分离**：底层因果图按故事时间，上层呈现按叙事时间

### 8.2 工程约束
- 基于 **pi 扩展生态**，不修改 pi 本体的 loader/config
- 完全分仓：pi 本体 / 扩展 / 小说工程各自独立仓库
- 扩展通过项目级 `.pi/extensions/` 加载（开发模式下 build 后同步）
- 创作内容与引擎数据同仓库共存
- 纯 TypeScript
- 事件输入唯一来源是用户口述

### 8.3 架构约束
- 调度器/角色/渲染器是独立 Agent 实例，与主会话隔离
- 子代理跨事件持久化，只接收增量状态更新
- 子代理直接输出结构化数据（扩散天然结构化）
- 信息差结构化（visible_entry_ids）
- 世界图是唯一状态中心
- 世界图 Git 版本管理，支持任意历史点回退
- 扩散实时写入，Impacts 用户控制触发
- 伏笔完全隔离，检索不可见

## 9. 新架构设计决策（brainstorming 进行中）

> 本节记录新架构 brainstorming 阶段逐步明确的设计决策。每条决策都是用户口述、整理记录。
> 决策一旦确定，就是硬约束，不可在实现阶段违反。

### 9.1 主会话角色定义（一切的起点）

**事件定义**：
- 事件 = 用户口述的剧情内容
- 事件可以是任意的——用户输入的宽泛度决定事件的粒度（见 2.7.1）
- 事件输入的唯一来源是用户口述

**主会话职责**：
1. **意图理解**：识别用户在干什么——写小说？写代码？闲聊？
2. **小说意图细分**：如果是写小说，识别具体操作——正删改查？其他需求？
3. **要素推理**：用户输入可能不完整（可能就是一句简单叙述），主会话需要根据上下文自动推理缺失要素，或查询相应内容来补全
4. **调度器交互**：把真正需要引擎处理的内容（含推理补全后的要素）交给调度器
5. **直接工具操作**：帮用户查询节点、修改节点等——只是帮用户解决问题，不参与叙事

**主会话的要素推理依据（选项 C）**：
- 对话历史（主会话自己的上下文）
- 世界图（通过工具查询）
- 当前章节文本（通过工具读取）

**主会话的工具权限**：
- 可查询世界图（节点、边、状态）
- 可修改节点/边（帮用户直接编辑）
- 可读取章节文本
- 可调用调度器触发叙事循环
- **不可**生成叙事文本
- **不可**参与角色扮演

**数据写入分层**：
- **引擎自然生产**：调度器 + 子代理通过扩散写入（有因果链、有事件溯源）
- **非引擎自然生产**：主会话工具修改 + 图 UI 修改（用户直接编辑，无扩散因果）
- 这两条是独立写入路径，融合问题在存储层解决
- 主会话修改和图 UI 修改是同一层级——都属"非引擎自然生产"

**主会话不参与叙事**：
- 主会话只负责沟通用户和调度器
- 不生成叙事文本
- 不参与角色扮演
- "不直接操作世界图"修正为"可直接操作世界图（帮用户），但不通过扩散写入世界图"——扩散写入是调度器+子代理的职责

**工程意义**：
- 这是整个引擎的入口，决定调度器拿到什么样的上下文
- 回答了难题 3（子代理扮演）的输入边界——调度器收到的不是原始用户输入，而是主会话处理后的结构化事件
- 回答了难题 10（用户编辑与引擎变更的融合）——主会话是用户编辑的入口，用户通过主会话工具直接改图，与引擎扩散写入是两条独立路径，融合问题在存储层解决
- 修复了 V2 的 Pending Gap（主会话引导 prompt 缺失）：主会话需要 system prompt 覆盖意图分类、mode 判断规则、章节判断、伏笔 payload 不暴露原则

**与飞书文档的对照**：
- 对应第 21 节（核心循环增加语义理解层）+ 第 22 节（意图分类）
- 但飞书文档说的是"语义理解层"，这里明确为"主会话"——主会话就是语义理解层的载体
- 五种意图（新增/修改/插入/查询/删除）对应主会话的意图分类职责

### 9.2 调度器角色定义

**调度器职责**：
1. **理解主会话发来的内容**：主会话已经做了意图分类和要素推理，调度器接收的是结构化事件
2. **世界图查询**：根据事件内容，查询各角色必要的信息、知识、世界背景
3. **信息差计算**：确定每个角色应该知道什么（Genette 聚焦理论的工程化）
4. **构建子代理提示词**：使用对应工具，为每个角色子代理构建专属提示词（含该角色可见的世界状态）
5. **启动子代理**：触发子代理进行角色扮演交互

**调度器的核心难题（对应难题清单）**：
- 难题 2（检索）：世界图查询的算法、深度、剪枝
- 难题 3（子代理扮演的前置）：信息差计算 + 提示词构建——子代理"应该有什么信息"由调度器决定

**调度器不做的事**：
- 不参与角色扮演（是子代理的职责）
- 不生成叙事文本（是渲染器的职责）
- 不直接和用户交互（是主会话的职责）
- 不做意图理解（是主会话的职责）

**信息差的工程化**：
- 每个角色应该知道什么 = 调度器为每个角色计算出的"可见世界状态子集"
- 对应飞书文档第 15 节"调度器定向分配知识"——按角色权限过滤世界条目
- 对应难题 3 的"子代理应该有什么样的信息"

**与飞书文档的对照**：
- 对应第 01 节（调度器职责：收集事件所需世界背景 + 拼接提示词交给执行器）
- 对应第 15 节（执行器架构升级：调度器定向分配知识）
- 但飞书文档的"执行器"在新架构中拆分为"子代理 + 渲染器"，调度器只负责构建提示词和启动子代理，不负责文本生成

### 9.3 渲染器角色定义

**渲染器职责**：
- 把子代理扮演生成的结构化数据，按一定规则渲染成最终的故事文本

**输入**：子代理输出的结构化数据（行为、对话、情绪状态变化等）
**输出**：故事文本（最终呈现给用户的叙事内容）

**与飞书文档的对照**：
- 对应第 15 节"渲染器将结构化数据渲染为最终叙事文本（对应骨骼/渲染双层架构）"
- 对应第 23 节"渲染器是有状态、有记忆的独立子代理实例"
- 对应第 16 节"渲染器提升到循环内部"——渲染器在循环内运行，不是循环外的事后处理

### 9.4 子代理角色定义

**子代理职责**：
- 作为"演员"，按照调度器分配的提示词以及指令，扮演好自己的角色进行交互

**输入**：调度器构建的提示词（含该角色可见的世界状态 + 指令）
**输出**：结构化数据（行为、对话、情绪状态变化等，供渲染器渲染 + 调度器扩散写回）

**子代理的核心特征**：
- **演员定位**：不是"智能体"，是"扮演者"——按调度器给的剧本和角色信息演绎
- **信息差隔离**：每个子代理只看到调度器分配给它的世界状态子集，不看到其他角色的完整状态
- **结构化输出**：不直接生成最终文本（那是渲染器的职责），输出结构化数据
- **跨事件持久化**：每个角色一个独立实例，跨事件保持对话历史和记忆，只接收增量状态更新（不全量刷新）

- 对应第 25 节"角色节点三层结构"——基础设定 + 动态记忆 + 当前状态

### 9.8 双图架构：事件图 + 世界图（重大决策）

**核心决策**：整体是两张独立的图，事件节点作为单独的节点，不和世界图一起放。

**两张图的职责**：

| 图 | 职责 | 内容 |
|---|---|---|
| **世界图** | 记录一切故事需要的背景信息 | 角色、设定、物品、地点、关系、规则等 |
| **事件图** | 记录整个叙事的流程 | 事件节点、事件间的因果关系、什么发生了什么变化 |

**事件图内可见的内容**：
- 事件本身（用户口述的剧情内容）
- 事件之间的因果链（事件→扩散→下一事件）
- 每个事件引发了哪些变化（扩散记录）

**与 Graphiti Episodic 节点的对比**：
- Graphiti 的 Episodic 节点存原始事件文本，但通过 MENTIONS 边连到 EntityNode，仍在一个图内
- 新架构将 Episodic 节点完全独立为"事件图"，与世界图物理分离
- 事件图通过引用（reference）连接到世界图节点，但不混在一起

**双图分离的工程意义**：
1. **职责清晰**：世界图是"状态"，事件图是"历史"
2. **回退独立**：事件图回退不影响世界图的稳定节点（用户的非引擎编辑保留）
3. **检索分离**：调度器查世界图获取角色信息，渲染器/用户查事件图获取叙事流程
4. **可视化分离**：世界图可视化看到的是关系网络，事件图可视化看到的是时间线/因果链
5. **写入分离**：世界图接受引擎扩散+用户编辑两条路径；事件图只接受引擎事件写入

**与难题的映射**：
- 难题 1（世界图记录）：世界图专注背景信息，职责单一，稳定性提升
- 难题 5（事件重写）：事件图独立后，回退只需操作事件图+对应的扩散写回，世界图稳定节点不受影响
- 难题 10（用户编辑融合）：用户编辑只作用于世界图，事件图是引擎独占写入

### 9.9 事件即状态变化记录（核心机制）

**核心澄清**：事件不仅是用户口述的内容时间线记录，也是整个世界图的状态变化记录。

**世界图只存储当前事件下世界的状态**：
- 世界图 = 当前时刻的状态快照
- 每个事件对应世界图的一个状态
- 事件 = 两个世界图状态之间的变化（diff）

**回放机制的解法**：
- 事件链 = 状态变化链
- 回放 = 从初始状态开始，按事件链依次应用每个事件的状态变化
- 回退到事件 E = 撤销 E 之后所有事件的状态变化，世界图回到 E 时的状态

**类比**：
- 事件图 = Git commit history（每个 commit 是一次状态变化）
- 世界图 = Working directory（当前文件状态）
- 回退 = git reset（移动 HEAD，working directory 相应变化）

**这个机制解决了什么**：
1. **难题 5（事件重写）的本质解法**：
   - 不需要在世界图上做 Bi-temporal 边失效（Graphiti 那套）
   - 事件图本身就是完整的状态变化历史
   - 回退 = 重放事件链到指定位置
2. **世界图的写入策略简化**：
   - 世界图永远只存当前状态，不需要保留历史版本
   - 每次事件扩散写入 = 直接覆盖世界图字段 + 在事件图中记录变化
3. **用户编辑融合（难题 10）的清晰化**：
   - 用户编辑 = 直接修改世界图当前状态（无事件来源）
   - 引擎扩散 = 修改世界图 + 记录事件
   - 重写事件时，用户编辑的部分不会被回退（因为没有对应的事件记录）

**事件节点的核心字段（基于此机制）**：
- `uuid`：事件唯一标识
- `content`：用户口述的事件内容
- `timestamp`：事件发生时间（故事时间）
- `created_at`：事件写入时间（事务时间）
- `cause`：上游事件 UUID（因果链）
- `diffusions`：状态变化记录列表，每条记录包含：
  - `target_uuid`：受影响的世界图节点
  - `field`：被修改的字段
  - `old_value`：修改前的值
  - `new_value`：修改后的值
- `narrative_text`：渲染器生成的故事文本（渲染层产物）

**待澄清的子问题（留待后续 brainstorming）**：
- 事件图存储格式？（JSON 文件 / JSONL 事件日志 / SQLite）
- 事件图是 append-only 吗？（重写时是软删除还是物理删除？）
- 事件节点的 `diffusions` 字段是否会过大？（一次事件可能扩散到多个节点多个字段，但单事件影响范围有限）

### 9.10 回退策略与用户编辑语义（关键澄清）

**核心澄清 1：回退机制**

- 一个事件内不可能变了几千个节点——单事件影响范围有限
- 事件图只存储每个事件中**状态的变化**（diff），不是完整状态
- 回退 = **按变化一步步反向撤销**（从当前状态向后走）
- 不需要从头重放整个事件链

**反向撤销的工程实现**：
- 每个事件节点的 `diffusions` 字段已经记录 `old_value` 和 `new_value`
- 回退到事件 E = 从当前事件开始，依次将 `new_value` 还原为 `old_value`，直到 E
- 时间复杂度 O(M)，M = 要撤销的事件数（通常很小）

**核心澄清 2：用户编辑的语义**

- 用户编辑影响的是**当前世界的状态**（直接修改世界图）
- 用户编辑产生的扩散**需要到下一个事件才生效**
  - 即：用户编辑不立即触发扩散，扩散在下一次引擎事件时由子代理处理
- 用户编辑不被记录为事件（它是非引擎写入）

**核心澄清 3：回退与重放的统一逻辑**

- **回退和重放是连续的两步操作，不是独立的场景**
- 完整流程：**反向撤销 → 到达节点创建位置 → 从该位置重新开始叙事**
- 不区分"重写普通事件"和"改节点基础属性"——都是同一个逻辑

**统一的回退重放流程**：
1. 用户发起回退（重写某事件 / 改某节点）
2. 引擎按事件链**反向撤销** diffusions（`new_value` → `old_value`）
3. 一直撤销到**目标节点创建的位置**（该节点首次出现的事件）
4. 从该位置**重新开始叙事**（重新跑子代理，生成新的事件链）

**关键含义**：
- 回退不是"回到过去就停下"，而是"回到过去 + 重新开始"
- 重放的起点 = 受影响节点的创建事件
- 重放 = 重新跑子代理，生成新的事件和扩散
- 旧的事件链在回退后被新的事件链替代（或保留为分支？待澄清）

**关键设计原则**：
1. **事件 = 状态变化的 diff，不是完整状态** → 事件节点轻量
2. **回退 = 反向撤销到节点创建位置 + 重新叙事** → 完整流程
3. **用户编辑不触发立即扩散** → 扩散由下一个引擎事件处理，避免冲突
4. **任何节点的创建事件都是潜在的重放起点** → 普适原则，不区分节点类型

**用户编辑与引擎扩散的写入语义（关键决策）**：

用户编辑影响当前世界状态，但扩散到下一个事件才生效。具体实现按"用户编辑优先"原则：

- **用户编辑直接覆盖世界图字段**（当前状态立即变化）
- **下一个引擎事件 E2 的子代理看到的是用户编辑后的状态**
- **E2 的 diffusions 记录 `old_value=用户编辑后的值, new_value=E2扩散后的值`**
- **回退 E2 时，世界图字段恢复为"用户编辑后的值"（即 old_value）**

**关键含义**：
- 用户编辑不会被引擎扩散"吞噬"——它作为 E2 的 `old_value` 被保留
- 回退 E2 后，用户编辑仍然存在（世界图回到 E2 之前的状态，即用户编辑后的状态）
- 用户编辑是"非事件写入"，不在事件图中记录，但通过 E2 的 old_value 间接保留

**举例**：
1. 初始：N.field = "value1"（E1 扩散写入）
2. 用户编辑：N.field = "value2"（直接覆盖，无事件记录）
3. E2 事件：子代理看到 N.field = "value2"，扩散后改为 "value3"
   - E2.diffusions = [{target: N, field: field, old_value: "value2", new_value: "value3"}]
4. 回退 E2：N.field 恢复为 "value2"（用户编辑保留）
5. 再回退 E1：N.field 恢复为 "value1"（用户编辑丢失，因为 E1 的 new_value="value1" 被撤销）

**回退机制的最终设计（Git 模式）**：

回退逻辑完全类比 Git 的回滚操作：

| Git 操作 | 引擎对应操作 |
|---|---|
| `git reset HEAD~N` | 反向撤销 N 个事件的 diffusions |
| Working directory 变化 | 世界图回到目标事件时的状态 |
| 旧 commit 保留 | 旧事件节点保留（不物理删除） |
| 新 commit 覆盖 | 用户新输入事件后，新事件覆盖旧事件 |
| `git revert` | 用户告诉引擎"按原来的事件重新跑" |

**两种重放模式**：

1. **手动重放**（默认）：
   - 引擎回退到目标事件后，等待用户输入新事件
   - 用户新输入的事件覆盖旧事件链
   - 类似 `git reset` 后重新 commit

2. **自动重放**：
   - 用户告诉引擎"按原来的事件重新跑"
   - 引擎按旧事件链的内容，依次重新执行
   - 类似 `git revert`（保留历史，生成新的反向 commit）

**节点创建事件的记录**：
- 节点创建时，记录是在哪个事件下创建的（`created_by_event: event_uuid`）
- 不需要复杂标记——一个字段就够了
- 反向撤销到某节点时，查 `created_by_event` 就知道是否到达创建位置

**关键设计简化**：
- 旧事件节点保留，不物理删除（和 Git commit 一样）
- 节点创建事件识别 = 简单的字段查询（`created_by_event`）
- 节点本身的删除 = 不需要特殊处理，反向撤销到创建位置时，节点的 `old_value = null`（创建前不存在），撤销后自然消失

**回退机制的工程实现：抄 Git 对象模型**

直接参考 Git 的对象模型和逻辑，针对双图场景实现最简版本。

**Git 核心概念映射**：

| Git 概念 | 引擎对应实现 |
|---|---|
| **Blob**（文件内容） | 世界图节点/边的当前状态 |
| **Tree**（目录结构） | 世界图的整体状态快照 |
| **Commit**（提交） | 事件节点（含 diffusions + 指向上一事件的 parent） |
| **Ref**（分支/HEAD） | 当前事件指针（指向事件链的 HEAD） |
| **HEAD~N** | 回退 N 个事件 |
| **`git reset`** | 移动 HEAD 指针 + 反向撤销 diffusions |
| **`git revert`** | 保留 HEAD，生成新的反向事件 |
| **`git reflog`** | 事件链历史（所有 HEAD 移动记录） |

**最简实现方案**：

1. **事件节点 = Git Commit**
   - `uuid`（commit hash）
   - `parent`（上一个事件的 uuid，对应 commit 的 parent）
   - `content`（用户口述）
   - `diffusions`（状态变化，对应 commit 的 diff）
   - `narrative_text`（渲染文本）
   - `timestamp` / `created_at`

2. **世界图 = Working Directory**
   - 只存当前状态
   - 每次事件扩散写入 = 直接覆盖字段
   - 不保留历史版本（历史在事件链里）

3. **HEAD 指针**
   - 一个字段，指向当前事件链的最新事件
   - 回退 = 移动 HEAD + 反向撤销 diffusions
   - 重放 = 从 HEAD 开始追加新事件

4. **节点创建事件 = `created_by_event` 字段**
   - 世界图节点带 `created_by_event: event_uuid`
   - 反向撤销时，查此字段判断是否到达创建位置

5. **旧事件链保留**
   - 和 Git 一样，旧 commit 永久保留
   - 通过 HEAD 移动实现"删除"，不物理删除事件节点
   - 支持 reflog 式的历史查询（可选，后续实现）

**回退操作的最简流程**：

```
def rollback(target_event_uuid):
    current = HEAD
    while current != target_event_uuid:
        event = load_event(current)
        # 反向撤销 diffusions
        for diffusion in reversed(event.diffusions):
            world_graph[diffusion.target_uuid][diffusion.field] = diffusion.old_value
        current = event.parent
    HEAD = target_event_uuid
    # 等待用户输入新事件，或按旧事件重跑
```

**优势**：
- 不需要复杂的版本管理（Bi-temporal、快照等）
- 直接复用 Git 的成熟心智模型
- 工程实现简单（事件链 = 单向链表 + HEAD 指针）
- 支持回退、重放、历史查询

**与 Graphiti 的对比**：
- Graphiti 用 Bi-temporal Edge（4 个时间戳 + 失效逻辑）→ 复杂
- 本方案用 Git 模式（事件链 + HEAD + 反向撤销）→ 简单
- 两者都能解决状态演化追踪和回退问题，但本方案更直观
